# @kanaries/graphic-walker@0.5.0 Patch Notes

This document describes the patches applied to `@kanaries/graphic-walker@0.5.0` via the `@kanaries+graphic-walker+0.5.0.patch` file. Since the patch file is regenerated by `npx patch-package` from the current `node_modules` state, this separate documentation file preserves the detailed rationale and original source locations for each fix.

These patches primarily address **internationalization (i18n) issues for Korean/CJK characters** in the Table (PivotTable) view.

> **Note**: All line numbers refer to the minified distribution file `graphic-walker.es.js`. Original TypeScript source locations are provided to facilitate upstream pull requests.

## Fix 1: CSV Export — UTF-8 BOM for Korean/CJK Characters

### Summary
Adds a UTF-8 Byte Order Mark (BOM) to CSV exports so that Korean/CJK characters display correctly when opened in Microsoft Excel.

### Original Source Location
| Item | Value |
|------|-------|
| **File** | `packages/graphic-walker/src/utils/save.ts` |
| **Function** | `export function download(data: string, filename: string, type: string)` |
| **Minified Location** | Line ~16956, function `Qft(e, t, n)` |

### Problem
When exporting data to CSV from the Table view, the file is created without a BOM. While UTF-8 encoded files are technically valid without a BOM, Microsoft Excel on Windows defaults to the system locale encoding (often CP949 for Korean, GB2312 for Chinese) when opening CSV files. This causes Korean/CJK characters to appear as garbled text (mojibake).

### Solution
Prepend `\uFEFF` (the UTF-8 BOM character) to the file content when the filename ends with `.csv`. The BOM signals to Excel that the file is UTF-8 encoded.

```javascript
// Before
var i = new Blob([e], { type: n });

// After
var data = t.endsWith(".csv") ? "\uFEFF" + e : e;
var i = new Blob([data], { type: n });
```

## Fix 2: SQL Lexer — Unicode (Korean/CJK) Identifier Support

### Summary
Extends the SQL lexer's `word` token pattern to recognize Korean/CJK characters as valid identifier characters, enabling the "Add Computed Field" feature to work with non-ASCII column names.

### Original Source Location
| Item | Value |
|------|-------|
| **Root Package** | `pgsql-ast-parser` (https://github.com/oguimbal/pgsql-ast-parser) |
| **Bundled Location** | The lexer is bundled into `graphic-walker.es.js` via rollup |
| **Minified Location** | Line ~17820, inside function `rmt()` |
| **Original Pattern** | `/[eE](?!')[A-Za-z0-9_]*\|[a-df-zA-DF-Z_][A-Za-z0-9_]*/` |

### Problem
The "Add Computed Field" feature uses `pgsql-ast-parser` to parse SQL expressions. The lexer's `word` token pattern only matches ASCII letters (`A-Za-z`), digits, and underscores. When users enter expressions with Korean/CJK column names (e.g., `"매출액" + "수량"`), the lexer fails to tokenize the identifiers, resulting in parse errors like:
```
Error: Syntax near "매" (unexpected token)
```

### Solution
Extend the `word` token regex to include:
- **Korean Hangul syllables**: `\uAC00-\uD7A3`
- **Korean Hangul Jamo (consonants/vowels)**: `\u3131-\u318E`
- **CJK Unified Ideographs**: `\u4E00-\u9FFF`

```javascript
// Before
match: /[eE](?!')[A-Za-z0-9_]*|[a-df-zA-DF-Z_][A-Za-z0-9_]*/

// After
const UNICODE_ID_CHARS = 'A-Za-z0-9_\\u3131-\\u318E\\uAC00-\\uD7A3\\u4E00-\\u9FFF';
match: new RegExp(`[eE](?!')[${UNICODE_ID_CHARS}]*|[a-df-zA-DF-Z_\\u3131-\\u318E\\uAC00-\\uD7A3\\u4E00-\\u9FFF][${UNICODE_ID_CHARS}]*`)
```

### Upstream PR Target
- **Primary**: https://github.com/oguimbal/pgsql-ast-parser (root fix in the lexer definition)
- **Alternative**: https://github.com/Kanaries/graphic-walker (if maintaining a forked/overridden lexer)

## Fix 3: Table View CSV Export — Row Order Matches Displayed Table

### Summary
Ensures that the CSV export from the Table view preserves the same row order as displayed on screen, sorted by dimension fields.

### Original Source Location
| Item | Value |
|------|-------|
| **File** | `packages/graphic-walker/src/renderer/index.tsx` |
| **Component** | `Renderer` (forwardRef) |
| **Location** | Inside `useEffect` that sets `csvRef.current = { download() { ... } }` |
| **Minified Location** | Line ~95867 onwards, inside `zcn` (SpecRenderer) |

### Problem
When users view data in Table mode with dimensions configured in Rows/Columns, the PivotTable component displays data sorted by those dimension fields. However, when exporting to CSV via the download button, the export uses the original unsorted data order from `viewData`. This inconsistency confuses users who expect "what you see is what you get."

### Solution
When `geoms[0] === 'table'`, sort the data array by the active dimension fields (from `encodings.rows` and `encodings.columns` filtered to `analyticType === 'dimension'`) before building the CSV string.

```javascript
// Before
const Ne = `${Ye.map((We) => We.name).join(",")}\n${E.map(...).join("\n")}`;

// After
let Ee = E;
if (f.geoms && f.geoms[0] === "table") {
  const Rd = (K.rows || []).filter((v) => v.analyticType === "dimension");
  const Cd = (K.columns || []).filter((v) => v.analyticType === "dimension");
  const Sd = [...Rd, ...Cd];
  if (Sd.length > 0) {
    Ee = [...E].sort((aa, bb) => {
      for (const d of Sd) {
        const av = aa[d.fid], bv = bb[d.fid];
        if (av === bv) continue;
        if (typeof av === "number" && typeof bv === "number") return av - bv;
        return String(av ?? "").localeCompare(String(bv ?? ""));
      }
      return 0;
    });
  }
}
const Ne = `${Ye.map((We) => We.name).join(",")}\n${Ee.map(...).join("\n")}`;
```

## Fix 4: Computed Field Editor — Korean/CJK Field Name Syntax Highlighting

### Summary
Fixes the syntax highlighting in the Computed Field SQL editor to correctly highlight Korean/CJK field names without false partial matches.

### Original Source Location
| Item | Value |
|------|-------|
| **File** | `packages/graphic-walker/src/components/computedField/index.tsx` |
| **Location** | Line ~31, inside `const SQLField = useMemo(() => { ... }, [vizStore.allFields])` |
| **Minified Location** | Line ~141013, component `PVn` |

### Problem
The Computed Field editor highlights field names in SQL expressions using a regex with `\b` (word boundary) anchors:
```javascript
new RegExp(`\\b(${fields})\\b`, 'gi')
```

The `\b` word boundary in JavaScript regex is ASCII-only — it matches positions between `\w` (`[A-Za-z0-9_]`) and `\W` characters. For Korean/CJK field names:
1. **No highlighting**: Field names like `매출액` are not highlighted because `\b` doesn't recognize Korean characters as word characters.
2. **False partial matches**: Inside longer Korean words, the regex may incorrectly match substrings.

### Solution
Replace ASCII word boundaries with Unicode-aware negative lookbehind/lookahead using Unicode property escapes:
```javascript
// Before
new RegExp(`\\b(${fields})\\b`, 'gi')

// After
new RegExp(`(?<![\\p{L}\\p{N}_])(${fields})(?![\\p{L}\\p{N}_])`, 'giu')
```

- `\p{L}` matches any Unicode letter (including Korean/CJK)
- `\p{N}` matches any Unicode digit
- The `u` flag enables Unicode property escapes

https://github.com/Kanaries/graphic-walker

## How to Apply These Patches

These patches are managed using [patch-package](https://github.com/ds300/patch-package).

### Automatic Application (Recommended)
Patches are automatically applied during `npm install` via the `postinstall` script in `package.json`:
```json
{
  "scripts": {
    "postinstall": "patch-package"
  }
}
```

### Manual Application
```bash
npx patch-package
```

### Regenerating the Patch File
If you modify `node_modules/@kanaries/graphic-walker/dist/graphic-walker.es.js`:
```bash
npx patch-package @kanaries/graphic-walker
```
> ⚠️ **Warning**: This regenerates the patch file from the current `node_modules` state, overwriting any manual edits to the `.patch` file. Always edit `node_modules` first, then regenerate.
